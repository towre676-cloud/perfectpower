# Exact incremental transport on an industrial corpus

The parallel mathematical push at `1b168bc` completed the integral norm-plane example u^3+4v^3=107 with the unique solution (-1,3), and added native cubic norm and shifted-basis transport. It retained an explicit distinction between the checked k=22 pilot and a complete curve theorem. This performance push preserves those results. It addresses the transport layer that executes industrial SMT-LIB scripts; it introduces no new number-theoretic theorem and changes no arithmetic assertion.

The previous 181-file portfolio trial solved fewer queries and cost more time. An industrial improvement must therefore be measured against the original solver strategy with the same query budget, rather than against a weaker or deliberately short-timeout control. The transport experiment uses the same Z3 version, QF_NIA header, original command text and incremental stack in both modes. The control submits one native call per command. The candidate groups consecutive non-query commands into bounded batches, flushing before every check-sat or check-sat-assuming. Stack commands remain in their original order. Query timeouts are configured immediately before each query and cleared immediately afterward. No query is moved across an assertion or stack operation.

Batching has an elementary sequence justification. Let s be the interpreter state and let T_c(s) be its transition for command c. The original transport computes T_cn(...T_c2(T_c1(s))...). A batch submits the same sequence to the interpreter in one call, retaining that composition. Query commands are barriers because their answers must be returned separately and their timeouts must not leak into later state updates. Batching does not eliminate the parsing or application of an assertion inside Z3, and therefore a reduction in native calls must not be presented as the same factor of solver speedup. Both modes omit observer commands, following the existing benchmark's answer-only scope. This does not provide model, proof or unsat-core forwarding.

The first frozen experiment used every file with its first min(8, query_count) queries, for 1,439 queries. Per-command replay made 2,191,327 native calls; batching made 6,687. Summed wall time fell from 300.454 to 295.383 seconds, a 1.7 percent reduction. The original solved 578 queries, and batching solved 579, with 26 paired gains and 25 losses. There were no SAT/UNSAT conflicts and every stream completed without a native error. The timeout-dependent answer differences show that one extra solved query is not evidence of stronger mathematics. The transport call reduction is substantial, but most elapsed time remains in solver queries and parsing. The report retains all rows and the exact pre-acceleration source hashes; matching source snapshots are included under `snapshots/`.

The second improvement targets command slicing. The existing scanner loops over every source character in Python. The alternative uses the regex engine to identify parentheses, complete string literals, complete quoted symbols and comments, then updates nesting only at structural parentheses. Quotes inside strings are escaped by doubling under SMT-LIB syntax. Comments and quoted names hide their parentheses. The result consists of exact original source slices, with no AST rendering or whitespace normalization. Unbalanced parentheses and unterminated quotes raise errors. The scanner is opt-in and does not replace the certificate parser globally.

Before solver timing, both scanners processed all 307,442,420 pinned corpus bytes, rather than only the selected prefixes. Their lists matched exactly for all 3,602,272 commands across all 181 files. Length-framed hashes of the command slices are retained per file. Summed scan time fell from 26.304 to 9.640 seconds, approximately 2.7 times faster, in this shared-machine experiment. This is a command-scanning result, not a solver result. Randomized lexical tests additionally cover comments, quoted names and doubled quotes. Corpus equality establishes compatibility for these particular inputs, not correctness for every possible SMT-LIB script.

The deeper paired replay experiment freezes the first min(32, query_count) queries in every file. Its candidate combines the fast scanner with bounded transport batches; its control uses the original scanner and per-command transport. Both use independent fresh Z3 contexts, the same 250 ms query allocation, and alternating execution order by file. Splitting the selected prefix, context setup, ingestion, native calls and query execution are included in replay wall time. Initial corpus acquisition, file reading and common prefix selection are excluded from both replay clocks and measured separately where applicable. A solver timeout is not a hard end-to-end wall-clock bound.

The complete deeper run selected 5,612 queries across all 181 files. Summed replay wall time fell from 742.481 to 707.361 seconds, a 4.73 percent reduction. The control solved 3,283 queries (2,069 SAT and 1,214 UNSAT), and the candidate solved 3,347 (2,134 SAT and 1,213 UNSAT). There were 260 paired gains and 196 losses, for a net gain of 64 solved queries. All streams completed without native errors, and there were zero SAT/UNSAT answer conflicts. Candidate wall time was lower in 128 of 181 files. This is a measured improvement on the declared single-host prefix cohort; it does not establish a universal speedup or uniform per-file dominance.

Native calls fell from 2,218,076 to 23,380, approximately a 95-fold reduction. Measured prefix scanning fell from 22.617 to 8.055 seconds, native ingestion from 58.562 to 54.831 seconds, and query time from 658.512 to 642.357 seconds. Changes in timeout-dependent answers contribute to the query-time difference; batching can also change interpreter allocation and solver search behavior despite preserving command semantics. The 64-query gain should therefore not be treated as a stronger logical solver or as a deterministic guarantee. No learned file selection, winner selection after timing, or alternative logic dispatch was used.

The command batch target is 262,144 characters. If a single source command exceeds that size, it is submitted alone. The entire source and command list are still held in memory, so bounded batching is not a constant-memory streaming parser. An invalid batch stops the stream before any later query can be recorded. This is answer replay, not a rollback transaction: the interpreter may process parts of a failed batch before reporting the error, but no answer from that failed continuation is accepted.

The runner writes checkpoints through a flushed, fsynced temporary file and an atomic replacement. Resume requires the same source manifest, engine hashes, protocol parameters, Python/Z3 versions and platform string. It checks source order and complete query rows. Checkpoints protect against an interrupted run in the same retained workspace; they do not survive deletion of the workspace itself. These checks detect mismatched inputs and accidental stale reuse, not adversarial tampering with a report. Committed reports and the source archive provide the durable research checkpoint.

Focused tests exercise incremental SAT/UNSAT/SAT traces, assumptions, randomized stack states, oversized commands, call bounds, malformed input, native errors, timeout barriers and stale-checkpoint rejection. The earlier formula and certificate suites are rerun. The new replay engine remains a separately callable performance path, and the slower strategy portfolio remains opt-in. Any improvement reported here belongs to front-end ingestion and transport in this harness; it does not establish a stronger decision procedure, a downstream verifier speedup or a commercial deployment result.
