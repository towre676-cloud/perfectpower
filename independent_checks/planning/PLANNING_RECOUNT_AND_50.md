# PerfectPower planning: independent recount of the solved cases, and a bounded exact attempt on the 50-project count

This report covers the Petersen R&D project-selection workload in `perfectpower` (`data/planning/petersen.json`, transcribed from Beasley's OR-Library `mknap1`). Everything below was produced by two new, portable, standard-library-only Python scripts written for this task — `recount_small_cases.py` and `attempt_50.py` — run against the repository read-only. They are committed here on the branch `muse/planning-recount-and-50-attempt`, as new files under `independent_checks/planning/`, for review by pull request against the repository's default branch; no existing repository file is changed. When run from that directory, both scripts default `--repo` to the repository root. Full machine-readable output is in `recount_results.json` and `attempt50_results.json`, with console logs in `recount_run.log` and `attempt50_run.log`. All arithmetic in the counting and optimisation code is exact (Python integers and `Fraction`); the single place floating point appears is in *proposing* Lagrangian prices for the branch-and-bound, whose validity never depends on the floats, as explained below.

## Part 1 — the solved public cases recount exactly, by independent methods

Three independent methods were implemented from scratch: a Gray-code brute-force enumeration of all 2^n assignments, a meet-in-the-middle counter over a cost-tuple dictionary, and a recursive counter that collapses a whole subcube whenever every remaining project fits in the remaining capacities. As a fourth source, the repository's own `CompletionPlanner` was also run on each case. Every method was compared against the repository's stated receipts in `receipts/planning/hybrid/benchmark.json` on four quantities — feasible count, exact maximum profit, number of maximisers, and the optimal point itself — and **every comparison agreed**:

| Case | Feasible count | Maximum | Maximisers | Methods agreeing |
|---|---:|---:|---:|---|
| petersen_6 | 28 | 3800 | 1 | brute force, MITM, collapse DFS, repo engine (gray) |
| petersen_10 | 644 | 87061/10 (= 8706.1) | 1 | brute force, MITM, collapse DFS, repo engine (gray) |
| petersen_15 | 22158 | 4015 | 1 | brute force, MITM, collapse DFS, repo engine (MITM) |
| petersen_20 | 422601 | 6120 | 1 | brute force, MITM, collapse DFS, repo engine (MITM) |
| petersen_28 | 208817578 | 12400 | 1 | collapse DFS (8,800,952 nodes, 14.0 s), repo engine (MITM) |

Beyond the headline quantities, the five receipt "bank" points in each case were replayed: all are feasible, none exceeds the optimum, and for the brute-forced cases their recomputed lexicographic ranks match the receipts' stated rank and reverse rank exactly. The separate petersen_6 receipt in `receipts/planning/petersen_6.json` also checks out: conditioning on the prefix `project_1 = 1` gives exactly the stated 12 completions with maximum 3300 and one maximiser. As a further cross-check, the frontier-interval counter built for Part 2 was run on petersen_28 as a test case and closed it exactly — 208,817,578 after 974,960 expansions — and on petersen_39 it produced the rigorous interval [367,416,693,865, 368,263,629,080] after 1,500,000 expansions, which contains the repository's stated count 368,072,359,571. **Conclusion for Part 1: the repository's stated counts, optima, tie counts and optimal points for petersen_6, 10, 15, 20 and 28 are correct as far as independent exact recount can establish, and the petersen_39 count is consistent with a rigorous independently computed interval.**

## Part 2 — the 50-project count: optimum proved, count narrowed to a rigorous interval, still open

The instance has 50 binary projects, 5 resources with capacities (800, 650, 550, 550, 650), all profits positive integers, and published optimum 16537. The two repository transcriptions of the instance (`data/planning/petersen.json` and `examples/planning/petersen_50_optimization.json`) were first verified to be identical, and the benchmark receipt's optimal point was replayed exactly: it is feasible, uses resources (800, 639, 549, 472, 650), and achieves profit 16537. The repository's native meet-in-the-middle index cannot count this instance because it accepts at most 42 independent binary variables.

**The optimum is now proved independently of the repository's solver.** A branch-and-bound written for this task, combining per-resource fractional-knapsack bounds with a Lagrangian bound, exhausted its search tree in 614,262 nodes (2.8 s) and certifies that no feasible portfolio beats 16537. The incumbent was not imported from the receipt: greedy heuristics only reached 15540, and the search itself found the 16537 portfolio (which coincides with the receipt's point; its tie count was *not* computed, so uniqueness is not claimed). The Lagrangian prices were proposed by floating-point coordinate descent at the root (dual value 16622.4) and then snapped to integers at scale 4096 — prices (27609, 6799, 9730, 0, 20972)/4096, giving an exact integer root bound of 16621. Because *any* nonnegative prices yield a valid bound by weak duality, the floating-point step affects only speed, never correctness; every pruning comparison in the search is exact integer arithmetic. This is a **proved** result, conditional only on the correctness of the new script, which the Part 1 recounts exercise heavily.

**The full feasible count remains open, but it is now pinned to a rigorous interval: 698,342,755,629,882 ≤ count ≤ 703,790,474,857,480**, a width of 5,447,719,227,598, about 0.78% of the lower end. This interval is computed, not estimated, and every ingredient is exact. Exact subset-sum distributions over all 2^50 portfolios were computed for each single resource and each pair of resources (integer-encoded dynamic programming; the largest pair distribution had 511,132 distinct sums). Each pair count is an exact count of the portfolios satisfying those two resources and hence a rigorous upper bound; the tightest pair, resources 4 and 5, gives 746,335,444,328,064. The cruder textbook bounds were also computed and are honestly weak here: the union bound lower estimate is negative (−74,998,198,678,296, truncated to uselessness) because violations of different resources are strongly correlated — a portfolio that overshoots one capacity tends to overshoot several — and the second Bonferroni truncation gives 1,519,596,209,399,948, worse than the trivial 2^50. The useful refinement is a best-first frontier expansion that branches on all 50 projects, largest normalised cost first: 295,206,809,990,662 portfolios sit in subtrees that were counted *exactly* (their remaining projects fit every remaining capacity, so the subtree is a complete subcube), and each of the 2,994,605 unexplored frontier nodes carries a rigorous interval whose upper end is the minimum of its exact single-resource and resource-pair-(4,5) suffix counts and whose lower end is its exact pair count minus the exact violation counts of the other three resources. Summing the exact part and the frontier intervals gives the interval above; at the root, before any expansion, the same machinery gives [88,254,953,452,712, 746,335,444,328,064], so the expansion bought almost all of the lower bound and about 4.25 × 10^13 of the upper.

**Budgets, stated as required.** The branch-and-bound was capped at 20,000,000 nodes / 1200 s and used 614,262 nodes / 2.8 s. The frontier expansion was capped at 3,000,000 expansions / 1200 s and used all 3,000,000 expansions in 64.1 s (plus about 25 s for the exact resource distributions and about 90 s of one-time suffix-grid construction inside the measured run). One extra-budget probe at 15,000,000 expansions (`frontier15m_probe.py`, log `frontier15m.log`) was **killed by the operating system (exit 137, out of memory) after about 373 s** on this 7 GB machine: the best-first frontier grows by roughly one heap node per expansion, so memory, not time, is the binding constraint for this strategy, and interval shrinkage beyond 3,000,000 expansions is unmeasured here.

**Precisely why the count is still open.** Three exact routes were tried or measured and each hits a concrete wall. Forward dynamic programming over cost vectors doubles its state count on essentially every project — a probe reached 14,633,022 distinct feasible cost vectors after only 24 projects with almost no collisions, so the state set is on course to track the feasible population itself rather than compress it. Subcube-collapse depth-first counting, which is fast up to 28 projects (8.8 M nodes), needed more than 160,000,000 nodes and 209 s on the *39*-project case without finishing in a probe run (the repository's native MITM did count that case, in 176 s, at the cost of about 1.57 billion tree-node visits), and the 50-project tree is far larger. A 25/25 meet-in-the-middle would have to materialise on the order of 2^25 half-portfolios per side before dominance or box-query pruning — beyond both the repository's 42-variable cap and what a standard-library Python program on this machine can hold. The frontier-interval method does converge to the exact count if run to exhaustion (it closed petersen_28 completely), but on petersen_50 its frontier still held 2,994,605 live nodes when the budget ended, and the memory wall above blocks simply enlarging the budget in this implementation. A disk-backed or depth-bounded variant of the same frontier method, a C implementation of the 5-dimensional box-counting join, or a smarter dominance order on the suffix distributions are the plausible next steps; none was completed within this task's budget, and no heuristic or sampled estimate is presented anywhere in this report as if it were the count.

## Classification of claims

**Proved** (exact exhaustive arguments, replayable by rerunning the scripts): the petersen_50 optimum is 16537; the recount values in Part 1. **Computed exactly, as rigorous bounds rather than a count**: the petersen_50 count interval [698,342,755,629,882, 703,790,474,857,480], all single- and pair-resource counts in `attempt50_results.json`, and the petersen_39 interval quoted above. **Heuristic only**: the greedy portfolio value 15540 used to seed the branch-and-bound (superseded by the proof), and the floating-point coordinate descent that proposed the Lagrangian prices (validity-independent, as argued). **Open**: the exact petersen_50 feasible count and its maximiser count.
