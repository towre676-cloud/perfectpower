# Exact Petersen portfolio exploration

PerfectPower Explorer now has a dedicated **Project portfolios** workspace beside its full research workbenches. It exposes the original 50-project Petersen instance through project cards, inclusive resource bounds, population totals, maximizing selections, conditional branch comparisons, rank lookup, and reproducible seeded uniform sampling. No command arguments are required. Original project names, ordering, resource names, integer costs and rational objective scores are retained. The score has no currency unit and is not a prediction of investment return.

A first calculation constructs the actual `CompletionPlanner` with `strategy: population`. The guided service imports the original request in `examples/planning/petersen_50_population.json`; it never substitutes the published count as a newly calculated answer. Adjusting minimum or maximum resource bounds creates a different specification and therefore a different planner. A single persistent worker retains one planner at a time. Successful subsequent queries for that specification reuse its residual partition and conditional caches. Restart, cancellation, timeout, OS process reclamation, or switching to another specification can require rebuilding. No cache is restored from untrusted saved answers.

The scope of conditional interaction is explicit: decisions fix projects in their original order, beginning with `project_1`. The next project's exclude and include populations partition the current conditional population. Every conditional result shows its own maximum and maximizing multiplicity; a conditional optimum need not equal the global optimum. The witness is decoded from the native original-coordinate mask, not fabricated from a project sorting or an approximate optimizer. Each displayed witness includes exact objective score and all five resource usages. Zero feasible completions display no selection. General arbitrary subsets are not offered through this prefix interface.

Ranks start at zero and use original-variable lexicographic order. Rank strings are parsed as arbitrary-precision integers in Python; the UI never converts population totals or ranks to JavaScript floating-point numbers. Seeded sampling draws a uniform integer rank through the planner's existing exact selection routine. A new rank can be expensive even after root construction. The retained fast query-bank benchmark describes already retained queries, not these arbitrary interactive choices.

The native arena remains 128 MiB, with the original request's per-attempt and cumulative work limits and bounded partition. The guided workspace uses a 20-minute wall-clock limit. It shows elapsed time, completed native calls, failed native attempts, completed partition nodes and search visits after native attempts return. Failed attempts mean the coordinator decomposed a subproblem or reached a work limit; their partial values are never reported as exact population totals. There is no invented percentage or estimated finish time. Cancellation kills the worker and discards its in-memory session; a later run starts cleanly.

The fresh guided-engine validation reproduced 702,508,860,122,761 feasible selections, maximum 16,537, and one maximizer. Root construction took 298.723 seconds in this environment, with the same 437,533,492 search visits and 189,856,527 setup cells as the original retained computation. An original 26-project zero prefix and its two branches checked the disjoint branch identity using the same retained planner. Rank zero completed in another 9.291 seconds. These are workload-specific measurements. The conditional query was especially easy; its timing does not characterize every prefix.

The focused test suite covers changed resource limits, no-cost empty selection, impossible conditional inclusion, exact rank validation above 2^53, seeded sampling, cache reuse, source identity and truthful progress. Browser checks run the real loopback server and native engine at desktop and 390×844 widths. They cover all 50 cards, edited bounds, empty conditional population, rank lookup, seeded sampling, evidence download, invalid-rank failure and recovery, and no uncaught JavaScript errors. Browser checks are not an Android-device or Windows-executable test.

Every completed run preserves `portfolio-request.json` and `portfolio-evidence.json` in the existing Saved runs folder. Evidence includes the exact specification, source input digest, native compiler/source/binary provenance, resource limits, conditional result, selected projects, and full partition receipt. Project decisions and edited bounds are saved separately in the existing private state directory and survive changing loopback ports. Neither the new worker nor a new repository extraction deletes existing runs. Android retains the portfolio compute service between successful queries, while ordinary research commands retain their isolated execution behavior. Android lifecycle termination can still reclaim the session.

This exact computation uses the existing tested native residual-polynomial kernel. The change adds progress observations and a guided coordinator; it does not establish a Lean proof of that kernel or a second independent unrestricted 50-project total. See [the population-planning mathematical account](POPULATION_PLANNING_MONOGRAPH.md) and [retained guided receipts](../receipts/planning/explorer/validation.json).

Native release status is recorded separately in `receipts/planning/explorer/release.json`. The original desktop and Android native libraries are bound to the current C++ source and export the population functions. A live research feed update cannot install the new interface or Java/Python executable changes in an already installed APK. Android upgrades must retain `com.perfectpower.explorer` and the existing private signing certificate; a newly generated key cannot update an existing installation while preserving its private data. An unsigned build is not advertised as an installable upgrade.
