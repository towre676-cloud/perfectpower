# PerfectPower Explorer: a desktop observatory for the complete repository

**Release purpose.** PerfectPower contains a large mathematical program rather than one narrow calculator. Integer equations, original-coordinate populations, project allocation, finite-machine semantics, exact geometry, generating functions, biological sequence studies and physical-model research share infrastructure but have different inputs and guarantees. A Windows explorer should make these connections discoverable while keeping the actual computations available. This release provides an executable desktop shell around the complete repository snapshot. It includes the sources, datasets, example inputs, theorem statements, documentation, retained visual artifacts and numerical engines rather than substituting a small synthetic demonstration for the project.

**The application window.** The Windows executable uses Electron to include its own Chromium rendering runtime. It opens a dedicated application window, first displaying a short startup screen while the bundled computation service starts, then opening the local observatory. The renderer has no Node access, uses an isolated context and does not need to fetch interface scripts from a CDN. The native setup executable carries the complete portable ZIP as an appended payload. It uses Windows' built-in archive support to install to a versioned Desktop folder, creates a shortcut and starts the explorer. If the folder already exists, setup creates a separately named folder instead of deleting the earlier installation. The installer and application are unsigned.

**A repository that remains whole.** The portable package retains every tracked file of the pinned main checkout, plus this release's desktop source and build products. It does not include Git's object database or developer caches. That distinction removes temporary material without cutting mathematical source or research data. The user can read the original README and monographs, inspect the exact C++ and Python engines, open data records, look at Lean statements and export any original file. The catalogue stores a path, title, kind, byte size and SHA-256 digest for each indexed file. Those digests identify packaged bytes; they are not a claim that every mathematical statement in those bytes is formally proved.

**The mathematical entrance.** The landing page displays two square-root sheets of w²=z³−2. For a complex input z=r exp(iθ), the mesh computes the principal argument and magnitude of z³−2, takes each signed square root, and projects the result to the three real coordinates (Re z, Im z, Re w). Surface color also depends on the imaginary part of w. Triangles crossing a discontinuity in the principal argument are omitted rather than drawing a false bridge across the chosen cut. This is a visual projection of a complex relation, not an intrinsic metric model of the entire Riemann surface. The user can rotate it manually. Reduced-motion preference stops automatic rotation. A locally bundled Poly Haven HDR studio environment supplies reflected lighting.

**The integer-point laboratory.** The equation page asks for coefficients in constant-first order, a power d and an integer interval. Its computation runs exact rational polynomial evaluation at every integer x in the displayed interval. Only integer polynomial values are passed to PerfectPower's integer-power-root test. For an even power, a nonzero accepted root gives both signs; zero is retained once. Odd powers preserve the signed root. The result is complete for that specified x interval. The real-curve viewport uses floating-point coordinates for display and highlights the exact returned points. Neither the plotted curve nor an empty bounded search is promoted into a global theorem. For supported global questions, the page links directly to the existing equation compiler workbench.

**Real examples from the repository.** Starting equations include the Mordell example x³−2, the effective quartic x⁴+x³+x²+x−199, the Pell relation 2x²+1 and the genus-two polynomial x⁵−x. The first retained search finds (3,5) and (3,−5); the quartic search finds (7,51) and (7,−51). These outputs come from the exact engine route, not decorative point lists embedded in the interface. Fractional coefficients retain their denominator conditions. Search inputs have explicit degree, power, coordinate-magnitude and interval limits. Large point populations are exported completely, while the viewport shows a bounded preview so that a broad search does not create hundreds of thousands of individually rendered spheres.

**Workbench breadth.** The build inspects the real argparse definitions in the main PerfectPower command interface and the separate BLAST interface. This creates forms with actual field names, required inputs, choice sets, default values and Boolean flags. The BLAST interface retains nested operation selection. This matters because a manually maintained small menu could silently lose commands as the project expands. Generated forms expose the existing command contracts rather than inventing new mathematical guarantees. Named starting inputs cover allocation, optimization, flow, matching, polygon triangulation, routing, Voronoi meshes, linear-product equations, Pell arithmetic and exact series compilation. The original JSON remains available for inspection and editing.

**Editing and execution.** A workbench can load a bundled input into an editor. The user chooses whether to run that edited copy; it is staged in a new run directory, preserving the bundled source. Advanced users can supply a JSON argument array. The engine starts Python subprocesses directly without passing arguments through a shell. Repository-relative input paths resolve to the included checkout. Each run records its request, exit code, elapsed time, standard output, error output and structured result when the output is JSON. A computation can continue while the user reads a monograph or browses another module. Saved runs support replay, inspection and export. The UI previews bounded portions of large arrays and strings; the saved files contain the complete captured output.

**Native arithmetic without a compiler installation.** The source project's planner and exact CNF counter ordinarily compile their C++ engines locally. A downloaded Windows application should not require a C++ development environment to make those operations usable. This release adds an optional shipped-binary path. Each DLL has a receipt identifying its C++ source SHA-256 and the DLL's own SHA-256. Before loading it, the Python loader checks both. Source checkouts without a shipped binary retain their existing compiler route. This binds the portable runtime to its included native source and detects accidental stale or damaged binaries. The receipt does not prove the compiler correct, prove the native algorithm in Lean, or replace the repository's mathematical evidence.

**The complete allocation result.** The included main snapshot contains the bounded-residual-polynomial population extension for the 50-project Petersen instance. The retained count is 702,508,860,122,761 feasible selections, with one maximizer. Its monograph, source input, independent checks, partition records and raw counting receipts travel with the explorer. The workbench can launch a fresh population computation through the same implementation. Its default recipe is marked as a long run; the user can choose a longer execution limit. The earlier measured Linux runtime is retained as historical evidence, not a promised Windows performance figure. The desktop work adds access and packaging, not a new claim of mathematical closure beyond the original engine's contract.

**Existing visual applications.** The explorer also opens the retained Room of Possibilities, public Budget Lab, differential-geometry viewer and BLAST reports. The Budget Lab calls the real local election engine through the explorer service. Source snapshots and queries remain inspectable. Other historical HTML artifacts keep their original behavior and dependencies. Self-contained artifacts remain self-contained; an artifact that originally depended on a remote service or CDN is not silently represented as an offline implementation of that service. The repository's Dresden observatory source is included, but its separate web build is not substituted for a newly built desktop subsystem.

**Search and source reading.** Repository browsing filters by file kind and directory, pages through the complete catalogue and searches titles, paths and short document summaries. The global search dialog also offers a content search: pressing Enter searches inside bundled text files and returns matching excerpts. Markdown renders as a reading view with local relative links rewritten to other included files. JSON opens as an expandable tree. Source text and large records can be read in successive portions, while original downloads retain all bytes. Images and PDFs can be viewed directly. Python source files remain executable from the source view, subject to their own arguments and dependencies.

**Locality and lifecycle.** The engine binds to the loopback interface on a dynamically assigned port and opens an authenticated local session. API calls require that session, check the local host and reject foreign write origins. The Electron window denies arbitrary navigation out of the local application. Closing the application signals the service to stop and closes active child processes. Run state is stored in the user's application data directory, so ordinary application updates do not depend on saving progress inside the installed source tree. The shell reuses a single application instance. This is a local desktop computation architecture; no cloud account or remote computation endpoint is required for the built-in workbenches.

**Dependencies and sources.** The release includes official CPython 3.12.10 Windows x64, Electron 44.7.0 and the declared numerical libraries numpy, scipy, sympy, mpmath, python-flint and z3-solver. The frontend uses Three.js, Lucide, Marked and DOMPurify. Exact version and acquisition hashes are retained with the package. Third-party notices accompany the source and runtime. The studio environment is a CC0 asset from Poly Haven. The original repository's code, documentation and dataset notices remain present. Including numerical libraries covers the declared Python extras, but it does not bundle every external executable used by historical research scripts.

**Validation and its limits.** The new engine-route checks exercise signed and fractional integer-point searches, input limits, large-integer JSON transport, shipped-binary digest loading, the global equation compiler, exact quartic solving, allocation, flow, triangulation, Pell arithmetic, series compilation, exact CNF counting and edited-input staging. Focused existing planner and model-counter suites also exercise the shipped Linux-native route. Browser checks drive actual forms, edited inputs, searches, source reading, embedded Budget Lab, preferences, saved computations and viewport widths. Screenshots are captured from the running interface using Chromium's software WebGL renderer. These checks establish concrete execution and layout behavior in the build environment. A native Windows GPU session and a physical user installation have not been exercised here; the Windows package's launch and graphics on the user's machine remain the first installation check.

**What this release does not finish.** Complete repository inclusion is broader than a custom visualization for every mathematical API. The universal workbench makes command families discoverable and executable, while specialized interactive graphics currently focus on equations and the retained visual applications. Lean, PARI, Sage and NCBI BLAST+ remain separate external tools. Their source interfaces and documented requirements are included, but the explorer does not manufacture their outputs when they are absent. Historical benchmark conclusions, open mathematical obligations and scientific interpretation limits are preserved in their source accounts. The practical next work is a Windows session on the intended machine, followed by deeper module-specific graphical editors built on the now-bundled engines.
