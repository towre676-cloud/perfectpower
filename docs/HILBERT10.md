# Perfect powers, computation, and the limits of solving equations

*A companion to [PerfectPower in the history of perfect powers](HISTORY.md). Repository facts are kept current with each release (`docs/RELEASE_CHECK.md`).*

Perfect powers have a surprising place in the story of computation. A square such as $49=7^2$ is easy to recognize. So is a cube such as $125=5^3$. Yet the ability to describe powers when the *exponent is allowed to vary* helped mathematicians prove that there can be no algorithm for solving every polynomial equation in integers. That is the connection between the everyday arithmetic of squares and cubes and the solution to Hilbert's Tenth Problem. It is also a useful way to understand what this repository is trying to accomplish: rigorous, effective answers for important families of equations, within a world where a universal answer machine cannot exist.

The distinction between a fixed exponent and a variable exponent matters. The statement $y=x^2$ is already a polynomial equation: $y-x^2=0$. Given particular integers $x$ and $y$, checking it is trivial. Even checking whether one given positive integer is *some* perfect power is an algorithmic task: there are only finitely many possible exponents to test. The difficult historical question was whether a relation such as $y=x^k$, with $k$ itself an unknown variable, could be described entirely through polynomial equations and additional integer unknowns. Matiyasevich's breakthrough supplied the missing exponential ingredient for that description. Perfect-power relations are one consequence and one clear way to see why the result matters; it would be too strong to call recognition of perfect powers by itself the source of undecidability. Mathlib's formal account makes this distinction visible: it has a theorem that variable-exponent powering is a Diophantine relation ([`Mathlib.NumberTheory.Dioph`](https://leanprover-community.github.io/mathlib4_docs/Mathlib/NumberTheory/Dioph.html), `Dioph.pow_dioph`). This repository connects to it in `PerfectPower/DiophBridge.lean`.

To see what "Diophantine" means here, imagine that we are allowed to write a polynomial equation using addition, multiplication, integer constants, and as many extra unknowns as we need. We then ask whether values of the extra unknowns exist that make the equation true. A relation among $x$, $k$, and $y$ is Diophantine if such an equation can describe exactly when that relation holds. For variable powers, the claim has the shape
$$y=x^k \iff \exists\, w_1,\ldots,w_r:\ Q(x,k,y,w_1,\ldots,w_r)=0,$$
with the appropriate domain conditions on the variables. The polynomial $Q$ uses no exponentiation with a variable exponent. The extra variables carry enough arithmetic information to express what that exponentiation would have said. The striking point is that a language built from addition and multiplication can describe a relation whose values grow exponentially.

Pell equations help explain how that can happen. An equation such as $u^2-Dv^2=1$, for a suitable nonsquare positive $D$, has solutions linked by multiplication of expressions $u+v\sqrt D$. Successive solutions grow rapidly, while the relation defining each solution is polynomial. Matiyasevich found a way to use the growth and arithmetic of related sequences to supply the missing link in the Davis–Putnam–Robinson program. The precise construction takes considerable work; one Pell equation on its own does not simulate an arbitrary computer. The important principle is that polynomial relations can constrain an entire sequence whose size behaves exponentially. Mathlib's formal development of this part of the story uses a Pell-based variant ([`Mathlib.NumberTheory.PellMatiyasevic`](https://leanprover-community.github.io/mathlib4_docs/Mathlib/NumberTheory/PellMatiyasevic.html)) and connects it to its proof that powering is Diophantine.

Hilbert's Tenth Problem asked for an algorithm that would accept an arbitrary polynomial equation and always determine whether it has an integer solution. "Arbitrary" carries much of the weight: the input polynomial can change from one run to the next, and it can have many variables. A particular equation might be simple. A whole well-chosen family might have an exact solution method. Hilbert asked for one procedure that would always finish with the right yes-or-no answer across the unrestricted collection. The answer is no. The combined theorem of Davis, Putnam, Robinson, and Matiyasevich shows that every computably enumerable set can be represented Diophantinely; as a consequence, such a universal procedure cannot exist. Matiyasevich's own account describes the 1970 result as the negative solution of Hilbert's problem ([Matiyasevich, *Hilbert's Tenth Problem*, preface](https://logic.pdmi.ras.ru/~yumat/H10Pbook/preface.htm)). Mathlib formalizes the powering step; it does not, as of the version used here, contain the full DPRM theorem or the undecidability statement.

"Computably enumerable" has a concrete meaning. Think of a computer program that prints a list of numbers, perhaps over an unlimited period. If a number belongs to the set, the program will eventually print it. For a number outside the set, watching the program for any finite time might leave us unsure whether it will appear later. The DPRM theorem says that membership in *any* such set can be translated into the existence of integer solutions to a suitable polynomial equation. This is where general polynomial arithmetic inherits the limits of computation. If we had a machine that always settled every polynomial solvability question, we could use it to settle questions about computations for which no such universal deciding machine exists.

There is an asymmetry in the ordinary search for integer solutions. If a polynomial has a solution, we can in principle enumerate integer tuples and eventually find one; substitution then verifies it exactly. If it has no solution, checking larger and larger boxes does not by itself establish that there is no solution beyond them. A theorem, a bound, a congruence obstruction, or some other complete certificate is needed to finish the negative case. This is the practical face of Hilbert's Tenth Problem. It does not say that negative answers are never provable. It says there is no single algorithm that will always produce the right answer and halt for every unrestricted input.

This point protects us from two tempting misunderstandings. One is that an easy question becomes difficult merely because it can be written in an undecidable mathematical language. Testing $y=x^2$ for supplied integers stays easy. The other is that the negative solution to Hilbert's Tenth Problem makes exact work on perfect-power equations futile. It does nothing of the kind. The impossibility result concerns a uniform algorithm for *all* polynomial equations. It leaves enormous room for strong methods for specified forms, fixed degrees, bounded classes, and carefully structured families. Much of number theory is the art of finding structure strong enough to turn one of those families into a problem we can actually finish.

Consider the curve
$$y^2=x^3+2.$$
It is already a polynomial equation in integers. Asking for every integral point is much harder than checking one proposed point, because "every" requires ruling out solutions at arbitrarily large coordinates. The repository proves in Lean that its integral points are exactly $(-1,1)$ and $(-1,-1)$, with no additional mathematical premise (`Generated/ClassLists/K2.lean`, `plus2`). It reaches that result through an exact class-list reduction, a proof about units in a cubic order, and a proof that a certain coefficient in every power of a unit vanishes only at exponent zero. Those are special facts about a specific arithmetic setting. They give a complete answer here without suggesting an algorithm for every polynomial equation. On natural numbers, `DiophBridge.plus2_nat` reads the same theorem as the statement that this fixed Diophantine set is empty.

The unit calculation is especially revealing beside the Hilbert's Tenth story. The theorem `Plus2.units_eq` describes every unit of $\mathbb Z[z]$, where $z^3+3z+2=0$, as a sign times a power of one chosen unit. On its own, that description appears to replace one infinity with another: the exponent can still be any integer. The next theorem, `Plus2.corner_eq_zero`, addresses exactly that infinity. Using a calculation at the prime $3$, it proves that the coefficient needed by the source equation can vanish only when the exponent is zero. This is a complete statement about *all* integer exponents. A test of the first thousand powers would offer evidence; the valuation argument supplies the reason no later power can escape.

There is a pleasing tension here. Pell-type growth helps explain how Diophantine equations can carry unbounded computational information. The repository's unit and recurrence arguments use similarly rapid growth and congruence behavior to bring a particular equation under control. The same broad arithmetic landscape supports both phenomena. There is no contradiction because the claims have different scope. A controlled family can have a powerful classification theorem even while the unrestricted universe of polynomial equations has no complete decision algorithm.

The positive-$k$ work in the repository makes that scope clearer. Thirty-nine curves $y^2=x^3+k$ came from a reduction of cubic forms to finite, kernel-checked lists, with reducible source equations solved exactly. The $k=2$ curve added an irreducible source equation and a genuinely infinite unit argument, and the same argument, proved once for every odd prime and every cubic order with one real embedding (`SkolemP.lean`, `RankOne.lean`), now closes further curves. Today ⟨LEAN_POS⟩ curves have complete integral-point lists with no extra premise. This is a meaningful step in mathematical coverage: the certificates establish why the lists are complete, rather than recording points found by a search. The axiom audit and the full clean-tree `make release-verify` are recorded in `docs/RELEASE_CHECK.md`.

The negative-$k$ work illustrates another honest boundary. Many curve theorems have complete conclusions *conditional on stated Matveev premises*. Under those premises, the generated Lean proofs carry out the remaining reductions and finite checks. This is valuable because the unresolved mathematical dependency is named exactly. It is also different from an unconditional proof. A reader can see which part the repository verifies and which part must still be supplied or formalized. That precision is essential if the project is to be useful beyond its authors.

What should a solver learn from all this? Its answer should carry its reason. A candidate integer point can be checked by substitution. A claim that a list contains *all* points needs a completeness argument. A claim that there are no points needs an obstruction or a complete exhaustion justified by a bound. For some families, the right answer is a finite list; for others, it is a parameterized infinite orbit; for still others, the best current outcome is a theorem conditional on an explicit mathematical premise. On unrestricted polynomial input, there must also be room for "unknown." Hilbert's Tenth Problem tells us why a truthful system cannot promise a terminating, correct yes-or-no result on every possible input.

This is where the repository's concern with exact hit semantics becomes more than a software detail. A tool that silently changes whether zero counts, whether exponents must exceed one, or whether it is checking natural rather than integer solutions can turn a true theorem into a false answer (`DiophBridge.isHit_nat_iff` states exactly when the integer hit predicate and the natural-number one agree). Likewise, a bounded search that returns "no hits found" has not returned "no hits exist." An exact input definition, a named theorem stating precisely what its certificate covers, and a separate verification step are what make the result reusable. The mathematics begins at that boundary: the theorem must speak about the question the user actually asked.

The connection to verification software follows naturally. A program proof often reaches an arithmetic obligation that a general SMT solver struggles to discharge. A library of exact lemmas for a recognized special form can simplify that obligation or give it a checkable certificate. The Why3-oriented experiment in the repository gives evidence worth developing: in the paired Z3 batch, solved obligations increased from 128 to 130 out of 134, with no previously solved obligation lost and lower total time. That is an experiment on a particular translation and workload, not a general solution to nonlinear arithmetic. Native Why3 proof sessions now replay from a clean checkout (`make why3-session`); adding the rule as a global lemma there discharges no new goal, so the selective policy, not the lemma alone, carries the benefit (`docs/ARITHMETIC_WORKFLOW.md`).

Matiyasevich's result therefore gives the project a sharper identity, not a grander claim of universal solving. It says precisely where completeness becomes impossible in general. The repository's opportunity is to find mathematically natural regions where completeness *is* possible, prove that a given input belongs to such a region, and hand a small exact reason to the next tool or researcher. This is useful to a number theorist trying to settle a family of equations and to a verification engineer trying to close a real proof obligation. Both need the same basic promise: an answer whose scope is explicit and whose decisive steps can be checked.

## Where each move stands

1. **The boundary as a theorem-level feature** — *done, in part* (`PerfectPower/DiophBridge.lean`).
   - `isHit_nat_iff` is the exact translation of the hit predicate on natural numbers.
   - `perfectPower_dioph` shows that variable-exponent perfect powers are Diophantine, through Mathlib's `pow_dioph`.
   - `fixedPower_dioph` and `mordell_dioph` cover the fixed-exponent relations, which are polynomial.
   - `plus2_nat` and `plus3_nat` are fixed Diophantine sets decided by complete-list theorems.
   - Not done: DPRM and undecidability, which Mathlib does not contain.
2. **A proof-carrying answer format** — *done.* Every compiler plan reports `answer` (complete list, generator, conditional, or unresolved) and `certificate`. The certificate lists the Lean theorems, the named premises, the Python steps, and `execution_verified: false`. The README shows one example of each answer.
3. **A reusable source engine** — *done for monic sources with one solution.* `SkolemP.corner_zero` covers any odd prime and any period. `RankOne` covers unit generation for any cubic order with a complex pair. The four candidates $k=4,33,49,81$ are closed, and more curves with them. `receipts/rank_one_blockers.json` records, for every remaining source, whether it is blocked by unit generation, the zero set, several solutions, or a nonmonic leading coefficient.
4. **One genuine software consumer** — *native sessions done; benefit not shown natively yet.* The selective policy in a native session is the next step.
5. **The map of what remains** — `receipts/rank_one_blockers.json`, `docs/GAP_ATLAS.md`, and the four-label status table in [HISTORY.md](HISTORY.md).
