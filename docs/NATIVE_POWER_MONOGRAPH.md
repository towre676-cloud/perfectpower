# Native effective bounds, proof-producing enumeration, and function fields

This checkpoint takes the proposed native architecture into working Lean code for a precise family. It proves an explicit global bound for every integer solution of y²=(x²+ax+b)²+k with k≠0, computes its complete finite list inside Lean, and emits a theorem for that list. It also extends the power-equation framework to polynomial rings over finite fields by composing Mathlib's Mason–Stothers/Fermat development with native enumeration of the remaining constant points. Neither implementation calls Sage, Singular, Python, a JSON certificate generator, or an external integer-point solver. The results are standard mathematical consequences formalized and automated here, not claims of newly discovered mathematics.

The existing repository already separated external discovery from proof checking. An external generator can propose a correct complete certificate whose correctness is then proved by a Lean theorem; its execution need not be trusted for soundness. Moving the generator into Lean improves integration, reproducibility and usability, but a change of implementation language alone does not discharge an analytic height hypothesis. This checkpoint therefore begins with the mathematical bound, then proves the finite enumeration complete, and only then supplies automation. It does not rename an assumed Baker or Matveev bound as a theorem.

Write p=x²+ax+b. From y²=p²+k one obtains (y−p)(y+p)=k. When k≠0 both factors are nonzero integers. A nonzero integer has absolute value at least one, hence each factor has absolute value at most |k|. The triangle inequality applied to their sum and difference gives |y|≤|k| and |p|≤|k|. These are global statements over all integers; they do not require x positive, a local search window, a genus computation, or a supplied point list. The proof is `NativeNearSquare.square_bounds`.

The remaining inequality bounds x. Put B=|a|+|b|+|k|+1. If |x|>B, then x² dominates |a||x|+|b|+|k|, so |x²+ax+b|>|k|. This contradicts the previous bound. Thus every point belongs to the rectangle −B≤x≤B and −|k|≤y≤|k|. `quadratic_bound` formalizes the domination argument with integer inequalities, and `explicit_bounds` combines both coordinate bounds. `points` filters the corresponding finite product of integer intervals by the original equation. `complete` proves that membership is equivalent to the equation for every x and y, provided only that k≠0. There is no hidden height premise.

For the nonsingular members of this near-square quartic family, the leading square describes two rational branches at infinity. The proof is an elementary effective Runge case, implemented arithmetically without formalizing the entire geometry of arbitrary places at infinity. It does not cover every curve satisfying a general Runge condition. It does establish an unconditional solver schema for an infinite parameter family, rather than a certificate for only one chosen polynomial. Extending the polynomial part beyond a monic quadratic, and replacing the constant remainder k by a lower-degree polynomial with coefficient-derived inequalities, is the next mathematical extension of this path.

The command `native_near_square name for a, b, k` accepts closed integer expressions, evaluates the coefficients in Lean, computes the bounded list using Lean lists and integer arithmetic, and declares an explicit finite set named `name`. It then declares `name_complete`, whose statement identifies every integer solution with membership in that finite set. The proof-producing tactic `decide_perfect_power a, b, k => expected` independently checks that the proposed set equals the mathematically complete bounded enumeration using `decide +kernel`, then applies the generic completeness theorem. It is deliberately a tactic for this supported family, not an arbitrary-polynomial tactic with an unrestricted name-to-capability promise.

The command elaborator uses Lean's metaprogramming evaluation to propose data. That elaborator is marked unsafe because the metaprogramming evaluator requires it. Its output is not accepted as a mathematical premise: the generated point-set equality is reduced and checked by the kernel, and the completeness theorem uses the proved bound. An incorrect proposed empty list is rejected in the focused audit. The command rejects k=0 before attempting to declare a finite completeness theorem; in that case y=x²+ax+b supplies a point for every integer x. No compiler-backed `native_decide` axiom is used by the generated proofs. Macros and elaborators are written in Lean; a custom C++ macro layer is unnecessary.

The examples cover x⁴+1, (x²+x)²+4, x⁴−1, x⁴+8, an empty shifted case, and a larger-coefficient case with a=23, b=−117 and k=8. The first five complete point sets are respectively {(0,1),(0,−1)}, {(0,2),(0,−2),(−1,2),(−1,−2)}, {(−1,0),(1,0)}, {(−1,3),(−1,−3),(1,3),(1,−3)}, and the empty set. Every list is generated by Lean before its equality and completeness are checked. The larger case demonstrates generation without manually specifying its expected points. Enumeration remains a finite brute-force computation with (2B+1)(2|k|+1) candidate pairs. A proved effective bound does not imply that every large input can be exhaustively reduced within practical memory and time.

The function-field extension begins with an existing Mathlib theorem, `Polynomial.flt`, derived from its Mason–Stothers development. Over a field K, if n≥3 and the image of n in K is nonzero, a polynomial solution fⁿ+gⁿ=1 must have constant f and g. Coprimality is proved from the equation itself: f^(n−1) and g^(n−1) provide the Bézout coefficients. The zero-coordinate cases are retained by comparing polynomial degrees of gⁿ=1 or fⁿ=1. `fermat_all_constants` therefore has no nonzero-coordinate premise left for the caller.

When K is finite, `constantPoints K n` enumerates all pairs of field constants satisfying the equation. `FunctionFieldPower.complete` proves that every polynomial-ring point comes from exactly this finite search under the stated exponent hypotheses. A concrete instance over F₇[t] completely solves f⁴+g⁴=1: the constant pairs are (0,1), (0,6), (1,0), (6,0), (3,3), (3,4), (4,3), and (4,4). The Fermat quartic in characteristic seven is the standard smooth degree-four example; this module proves its polynomial-point classification, not a formal theorem about its geometric genus. The field list is checked by kernel computation over `ZMod 7`.

Positive characteristic requires an explicit exception. If p is the field characteristic, Frobenius gives tᵖ+(1−t)ᵖ=1 for every polynomial t. The theorem `frobenius_family` proves this directly in Lean. The nonzero-exponent condition in the finite theorem excludes exactly this use of the characteristic exponent. It would be incorrect to say that unconditional polynomial abc alone supplies a finite solver for every function-field power equation. Separability, derivative-zero cases, coefficient dependence and the actual form of the equation remain part of the mathematical contract.

The larger research proposal contains additional projects that this checkpoint does not claim to finish. General Runge bounds require hypotheses about the relevant branches and explicit coefficient estimates. Baker/Matveev requires formal logarithmic-height and linear-form lower bounds; the repository's named analytic premise families remain open. Classical Chabauty–Coleman uses a Mordell–Weil rank condition below the genus and bounds rational-point counts; it is not, by genus alone, a universal integer-coordinate height cutoff. General rings of integers additionally require native arithmetic for ideals, units and integral bases. These foundations should be advanced as separate theorem-bearing modules rather than hidden behind a catch-all solve command.

Yun decomposition, certified continued fractions and general Pell automation are not implemented by this tactic. Browser deployment, WebAssembly packaging, Rust/C++ bindings and GPU scanning are also separate engineering work. Lean's documentation includes Emscripten/WebAssembly among its supported platforms, but this package has not been compiled or tested in a browser. A GPU candidate scan above 10¹² would need an algorithm and measured throughput, and would still not establish completeness without the relevant proved bound. This checkpoint supplies neither a browser-kernel claim nor a GPU-performance claim. It preserves the other session's completed k=22 classification and our previously measured industrial replay work.

The focused validation compiles the mathematical modules, the native tactic, and the example audit using Lean 4.20.0 with the repository's pinned Mathlib revision. The audit prints the axioms of the generated theorems, the generic coordinate bound, the generic integer enumeration, the function-field completeness theorem, the Frobenius family, and the F₇ classification. Accepted proofs use only propext, Classical.choice and Quot.sound. Validation is focused on these new modules; it is not a claim that the entire large repository was rebuilt in this session. The computation source, proof source, transcripts and validation receipt are included with the complete source archive.
