# Exact hybrid completion planning

PerfectPower v0.9.8 turns the preceding completion planner into a hybrid engine for independent binary allocations. It adds weighted permutation compression, an optional native meet-in-the-middle index, and a separate optimization-only search. These additions address distinct costs. Repeated identical choices can be represented by their selected multiplicities. Asymmetric choices can be split into two smaller populations whose resource vectors are joined exactly. Finding one maximum can avoid constructing a complete population altogether. The original dynamic program, Gray enumeration, generating-function route and protected compatibility quotient remain available.

The practical result is a larger supported query space and a measured optimization win on a particular public instance. This release does not establish universal superiority over conventional solvers. Its full feasible count for the 50-project public case remains unresolved. Its optimizer also remains slower than OR-Tools on several smaller cases. The benchmark ledger keeps those outcomes alongside the wins, including initialization, index construction, cached-query behavior and memory scope.

**The mathematical contract.** An allocation assigns a zero or one to each original named project. Each resource has an inclusive lower and upper bound, and each project contributes a nonnegative integer cost to every resource. Profit is an exact rational number; negative profits and zero costs are permitted. A plan is feasible precisely when all resource totals satisfy their intervals. The completion interface counts every feasible original tuple, reports the exact conditional maximum and its number of ties, selects tuples by lexicographic rank, computes the inverse rank, and samples by choosing a uniform integer rank. Optimal selection and sampling refer to the global maximizing population. A conditional maximum under a prefix need not equal the unrestricted maximum.

The new routes preserve this contract rather than changing the population to a set of equivalence classes. Projects keep their original identities and positions. Two interchangeable projects still give two distinct plans when exactly one is selected. Prefixes continue to mean assignments to the first original variables. Returning a canonical orbit representative without its multiplicity would violate counting, tie counting and uniform sampling. Sorting variables internally without restoring their original order would violate ranking. The implementation treats these as functional requirements.

**What Galois theory contributes.** Tom Leinster’s *Galois Theory*, arXiv:2408.07499, develops group actions, polynomial conjugacy, splitting fields, fixed fields, the Galois correspondence and finite-field automorphisms. Its group-action viewpoint helps articulate a useful question: which transformations preserve everything the query observes? A field automorphism and a permutation of interchangeable projects are different mathematical objects. The project-permutation route here uses a finite group action on binary assignments; it does not compute a splitting field or invoke the Galois correspondence to solve a knapsack problem. The paper supplies conceptual structure, not a published benchmark-winning allocation algorithm.

This distinction matters for attribution and for engineering. PerfectPower already has polynomial root-orbit machinery and compatibility-state reduction. The new weighted route concerns another layer: symmetries of original decisions, including the number of original decisions represented by each compressed state. Compatibility reduction can merge states with the same future behavior while preserving individual action paths. Decision symmetry can merge interchangeable choices while preserving how many assignments realize a multiplicity. These reductions can be useful together in future work, but this release deliberately limits decision symmetry to independent binary allocations without a compatibility machine.

**Weighted permutation compression.** Projects are grouped only when their complete resource-cost vectors and exact profits agree. For a group of size \(s\), selecting \(k\) projects contributes \(k\) times its cost vector and profit, and represents \(\binom{s}{k}\) original assignments. The fold sums weighted feasible counts and maximizer counts, keeping the largest attainable exact score. A prefix removes committed projects from their groups and subtracts their resource usage. Thus the available group sizes change with the query: a symmetry valid before a prefix is not blindly reused afterward.

For 64 interchangeable unit-cost, unit-profit projects with capacity 32, the feasible count is \(\sum_{k=0}^{32}\binom{64}{k}\), and the maximizing count is \(\binom{64}{32}\). Increasing capacity to 64 gives exactly \(2^{64}\) original plans. These counts exceed the size of a machine-word population index, but Python integer arithmetic retains them exactly. Tests check endpoint and middle ranks, reverse ranks, optimal ranks and all original identities. The representation does not materialize every plan. It visits a small set of multiplicity states and reconstructs a requested original assignment using completion counts.

The public Petersen allocation cases contain no identical project cost columns, no fully interchangeable projects and no identical resource rows. Consequently this route does not explain the speed gains on those cases. That is a useful boundary: symmetry detection must find a real invariant, and an instance without the tested symmetry should take another route. General graph automorphisms, coupled resource/project permutations and arbitrary group stabilizer chains are not implemented here.

**The asymmetric allocation index.** Meet-in-the-middle splits the original variable sequence into contiguous left and right halves. It enumerates right-half records containing exact resource usage, exact scaled profit and the original binary mask. Records exceeding an upper bound are discarded safely because all resource costs are nonnegative. A balanced spatial tree stores coordinate minima and maxima, mask bounds, population size, maximum score, tie count and the smallest maximizing original mask for each node.

For each feasible left-half assignment, the remaining resource intervals define a box query over the right records. A node entirely outside the box contributes nothing. A node entirely inside both the resource box and the requested mask interval contributes its whole stored aggregate. A boundary node is split, or its small leaf is checked record by record. The aggregation combines counts and conditional maxima without discarding distinct masks. The first complete join also retains a segment index over left-half blocks. Later prefixes ending in the left half can query this segment index; prefixes extending into the right half fix a left assignment and query the right tree.

This design is especially useful when a large fraction of records can be accepted or rejected in blocks. It is not a dimension-independent logarithmic algorithm. Correlated or poorly separated resource vectors can force many boundary visits. The 39-project case requires roughly 1.57 billion visited query nodes and takes minutes to compile on this machine. Calling the method meet-in-the-middle does not make that expense disappear. The retained index makes subsequent queries much cheaper, but construction remains part of the cold-workflow measurement.

The native implementation accepts at most 42 independent binary variables, with auto-routing limited to 40, and at most 16 resources. Default budgets allow 1,100,000 right records and 2,000,000,000 query visits; callers can reduce them, and the record maximum is 2,200,000. Exhausting a budget raises `WorkLimit`; a partial population is never returned as complete or empty. The 50-project case exceeds the supported MITM variable range. Large rational objectives also retain a safe boundary: the common-denominator integer profits must have total absolute value at most \(2^{60}\). Unsupported automatic native objective scaling routes to the ordinary exact methods instead.

**Optimization without population construction.** `optimize_allocation(specification)` searches independent binary allocations for one exact maximizer. It supports up to 64 projects and 16 resources and returns the original-coordinate witness. It does not return a feasible count or a maximizer count. That difference is explicit in its schema and scope. A completed bounded search reports `optimal: true`; exceeding the visit budget raises `WorkLimit`, even if an incumbent has already been found.

Variable ordering favors positive profit relative to normalized resource use. The ordering influences search speed, never the definition of feasibility. Each resource supplies a fractional-knapsack upper bound on the remaining integer objective. The implementation sorts the available positive-profit items by exact profit/cost ratio, fills the remaining resource capacity and takes the integer floor of the fractional remainder. Ignoring other constraints only enlarges the relaxed feasible set, so the bound remains an upper bound. Taking the minimum across resources strengthens it. Zero-cost contributions, negative profits and lower resource requirements are handled explicitly.

A second bound uses nonnegative resource prices. For remaining capacity vector \(b\), remaining item profits \(p_j\), costs \(c_j\), and nonnegative prices \(\lambda\), the remaining optimum is at most
\[
\lambda\cdot b+\sum_j\max(0,p_j-\lambda\cdot c_j).
\]
Coordinate descent proposes useful prices. It uses floating-point arithmetic only to choose these heuristic coefficients. The coefficients are then converted to nonnegative fixed-scale integers, and every actual pruning comparison is evaluated in exact signed 128-bit arithmetic. No approximate LP value is accepted as an exact answer, and no numerical tolerance decides feasibility. Any nonnegative prices yield a valid bound; poor prices cost performance rather than correctness. The Python wrapper independently replays the returned resource totals and rational profit in original coordinates.

**Routing and interfaces.** Automatic routing first recognizes interchangeable independent binary choices. Small capacity grids can retain the ordinary dynamic program. Supported asymmetric binary cases with at least 15 variables use the native index when a suitable compiler is available and exact scaling fits its arithmetic budget. Smaller binary cases retain Gray enumeration; other allocations retain enumeration, generating functions or the general completion fold according to the preceding rules. Positive-cost action words and compatibility-constrained allocations continue through the existing exact fold.

The optional kernel is bundled as `native/completion_planner.cpp`. A process compiles and loads it once using a C++17-capable `g++`; the Python package still declares no required third-party Python dependencies. The tested environment is Linux with GCC 13.3. The implementation uses GCC-compatible 128-bit integer types. When the compiler is absent, automatic routing retains the Python methods. An automatic native compiler failure also falls back to the supported Gray or DP route. Explicit native requests expose a work-limit error. No native binary is checked into the repository.

The usual `plan` command accepts existing requests unchanged. An optimization-only request sets `optimization_only` to true and supplies an empty query list. The saved example `examples/planning/petersen_50_optimization.json` is directly runnable with `python -m perfectpower plan` followed by that path. JSONL clients can use operation `planning_optimization` with `args.specification`. Complete planners retain the catalogue interface and the existing `count`, `completions`, `select`, `rank`, `sample`, `optimize`, `page`, `summary` and `evidence` methods. Cached query results are bounded and copied on return so callers cannot mutate stored plans.

**Independent comparisons and results.** The workload is the seven historical Petersen R&D allocation instances distributed in J. E. Beasley’s OR-Library `mknap1` dataset. It is public historical test data, not evidence of a production deployment. The original text and lossless transcription remain in `data/planning`. All seven optimization results match the published optimum. The complete-query bank checks total count, maximum and tie count, five selected original plans, their reverse ranks and their prefix counts.

The small complete workflows are compared with the preceding independent Python Gray index and a native exhaustive index. The native baseline recursively enumerates original assignments with resource pruning, then indexes feasible records; it is not an unpruned artificially slow loop. Both native variants use the same tested aggregation interface. The 28-project total is independently reproduced by a different recursive reference that collapses whole feasible binary subcubes. The 39-project total has no second independently reproduced global count in this release; independent recursive checks instead cover the five selected plans’ 20-variable prefixes, including conditional counts, maxima and ties.

Cold measurements include index construction and the complete five-query bank. Native compilation is initialized separately and its measured time is retained in the ledger. Warm measurements reuse a compiled model and average 20 banks per trial. Three trials rotate variant order. Optimization-only comparisons alternate native and OR-Tools order and include model preparation and exact witness replay. They are separate from counting comparisons: OR-Tools’ knapsack baseline returns one optimum, not a complete population. A native exhaustive baseline removes the explanation that the entire cold-workflow improvement comes merely from using a faster implementation language.

On the largest optimization instance, the median native time is about 61.1 times faster than the measured OR-Tools baseline. On the 20-project cold complete workflow, the native exhaustive comparison is about 29.6 times slower than MITM. OR-Tools still wins the five smaller optimization cases, and the independent Python Gray index retains faster warm banks on the four small counting cases. Compilation and loading cost 2.41 seconds once per process, so a single tiny request can be dominated by startup. These qualifications are part of the result.

The ledger includes Linux cumulative process peak RSS after each case. This is a process-level high-water mark, not isolated memory for every variant; it includes earlier imports and earlier workloads, and excludes compiler-child memory. It must not be interpreted as an individual kernel’s memory footprint. A separate `hybrid/memory.json` ledger runs fresh processes for selected variants. The 20-project MITM workflow peaks at about 16.6 MiB, the native exhaustive baseline at 95.7 MiB and the Python Gray baseline at 76.2 MiB. The 50-project optimization-only runs peak at about 16.6 MiB for the native solver and 204.1 MiB for OR-Tools in these worker processes. These measurements include each worker’s interpreter and imports and exclude compiler-child memory. Reproduce them with `python python/run_planning_hybrid_memory.py` and the checkout Python path. The earlier isolated v0.9.7 measurements remain historical receipts. Neither timing nor memory results establish a general industrial solver advantage.

**Validation and remaining work.** The focused suite runs 124 tests, with 122 passing and two optional Mathlib checks skipped. New tests compare the hybrid routes against exhaustive original-coordinate enumeration over 32 varied small native models, including fractional and negative objectives, lower capacity bounds, ties, empty populations, ranks and prefixes. Symmetry tests vary group membership and compare all selected plans against enumeration. Separate checks exercise work limits, native arithmetic limits, compiler fallback, copied cache results, original input validation and the optimization-only request contract. The six preceding Lean transport theorems remain compiled proofs about compatibility transport; they do not verify the new C++ tree, dual search or Python symmetry fold.

The immediate mathematical gap is the full 50-project count. More sophisticated orthogonal range counting, better decision ordering, compressed dominance structures and resource-specific convolution could address it, but this release does not claim to have done so. General decision symmetries with compatibility machines, formal weighted-fiber transport and broad native-kernel verification also remain future work. The useful advance is already concrete: two previously unresolved public counts become executable, and the largest public optimization case shows a substantial repeatable speed advantage while the smaller losing comparisons remain visible.

The reproducible command is `make planning-hybrid-benchmark`, which runs the public comparisons and the large count with three optimization trials. `make planning-test` runs both planner test modules. Installed packages include the native source and public dataset through the existing runtime-asset build. The benchmark receipt binds its native compiler, flags and source hash. Repository validation records the final source hashes, test scope and package smoke checks. Full historical Lean and research workloads are not rerun merely because this planner changed.
