# An exact space you can navigate

PerfectPower's latest mathematical layers are useful together. Weighted-budget populations represent resource allocations. Rational generating functions count them at every budget. Exact linear realizations turn the same coefficient sequence into the output of a machine. Intertwining maps preserve that output while reducing the machine's state dimension. Analytic majorants bound an actual infinite remainder. Finite telescoping and exact stored-value arithmetic give two further routes into the arithmetic engine. This exhibit connects those capabilities through a reproducible calculation and an offline interface. Its purpose is to make the mathematical relationship observable, with exact results and measured costs attached to a small, completely specified problem.

The changes inspected before this work are the releases through commit 7b7ffdc, version 0.9.6. Since the original Wilf integration, the repository added exact rational-series minimal realizations, series tail certificates, IEEE-754 binary64 integer decoding and accumulation, polynomial power queries at stored values, finite binomial-sum discovery with endpoint replay, and additional Lean mathematical foundations. The retained series audit records 69 named declarations across its foundation and generated modules. This showcase verifies that every source hash in that audit still matches. It does not recompile those modules or convert its own Python results into new checked Lean instances.

## The resource question

Let x and y be nonnegative integers. Resource x costs one unit and resource y costs two units. At budget B we ask for all allocations satisfying x+2y=B. Distinct original pairs remain distinct members. We order them lexicographically by x, starting with rank zero. The generating function is

\[F(z)=\frac{1}{(1-z)(1-z^2)}.\]

The factor for x is 1+z+z²+⋯; the factor for y is 1+z²+z⁴+⋯. Multiplying these factors makes the coefficient at budget B count exactly the admissible pairs. This is a count of allocations. It does not count the order in which individual resource items were obtained. Ordered action histories generally have different multiplicities and a different generating function. Keeping that distinction explicit prevents an attractive but false connection between a resource population and a path-counting model.

At B=10¹² the count is 500,000,000,001. The member at rank 100,000,000,007 is x=200,000,000,014 and y=399,999,999,993. Substituting these coordinates gives the original budget exactly; reverse ranking returns precisely the requested rank. The general population engine derives its count through rational coefficient access, and its selection through coefficient differences and coordinate bisection. It does not construct a list containing half a trillion members.

An independent calculation eliminates y. The allowable x values are B modulo 2, followed by steps of two through B. This immediately gives floor(B/2)+1 members and identifies each ranked member. That arithmetic progression is used as an independent oracle. It is deliberately simpler than the engine being demonstrated. For this particular two-coordinate family, the closed formula is the most efficient specialized implementation. The value of the general engine is that its factor construction and coefficient operations also support declared lower bounds, upper bounds and residue restrictions within the documented degree and arithmetic budgets.

The second population adds x≡1 modulo 3 and y≡2 modulo 5. Write y=2+5t. Then x=B−4−10t, and the restriction on x requires t≡B−5 modulo 3. Consequently admissible original x coordinates form a progression with step 30. At budget 10¹² there are 33,333,333,333 members. Both the generating-function engine and the independent elimination route agree on the count and selected coordinates. Small populations are exhaustively checked by enumeration, including budgets where these restrictions produce no member.

A further saved calculation keeps four original coordinates, with weights (1,2,1,2), at the same trillion-unit budget. Its generating function is F(z)². At even budget B=2m its count is (m+1)(m+2)(2m+3)/6; at odd budget B=2m+1 it is (m+1)(m+2)(m+3)/3. The default count exceeds 4×10³⁴ members. The general population engine selects the member at rank 10³⁰. An independent rank calculation sums explicit suffix counts, and small four-coordinate populations are exhaustively enumerated to check that oracle. This makes the selected member inspectable without reducing the whole exhibit to a single one-dimensional progression. The four-coordinate result is saved separately; the live browser controls retain their stated two-coordinate scope.

## Selection and optimization

The optimization question is to maximize a x+b y. On the same budget line, the objective is ((2a−b)x+bB)/2. Its exact slope decides which endpoint maximizes it. Positive slope chooses the greatest admissible x; negative slope chooses the least admissible x. Zero slope means that every population member ties. The showcase reports the maximum, an original-coordinate maximizer, its rank and the total number of maximizing members. Reporting the tie count matters: returning one endpoint alone would conceal the actual answer for a flat objective.

For the default objective 3x+5y, the maximum at B=10¹² is 3,000,000,000,000, attained uniquely at (10¹²,0). The interface also offers x+3y, which favors y, and x+2y, for which every allocation ties. These are exact optimizations for the stated two-coordinate family. The new adapter does not claim a general integer-programming optimizer. It uses the existing population engine to recover the endpoint selected by the proved elementary slope calculation.

All browser queries use JavaScript BigInt. Budgets and ranks enter as decimal integer strings and remain integers throughout count, coordinate recovery, rank and objective calculations. The supported budget is below 2⁶⁴, matching the coefficient engine's index contract. A rounded fraction is used only to position the selected rank on a small display graphic. It cannot affect an answer. Empty populations, malformed inputs and out-of-range ranks produce an explicit error. The browser implements the two arithmetic-progression specializations; it does not execute the Python generating-function compiler. Saved Python results are embedded separately so the two paths can be inspected.

## The same answer in a smaller machine

Expand the count function as a sequence a_n=floor(n/2)+1. Its denominator is 1−z−z²+z³, so a_{n+3}=a_{n+2}+a_{n+1}−a_n, with initial values 1,1,2. An exact three-state companion realization stores three consecutive values and advances this recurrence. Its first coordinate is the population count at the corresponding budget. Although an entry of its transition matrix is negative, the count sequence is nonnegative. This machine represents a response sequence; it is not presented as a physical collection of nonnegative state quantities.

The six-state source extends this realization with three hidden states. Those states receive the visible state values and circulate through a three-cycle, so they genuinely evolve. They do not feed back into the visible subsystem or into the protected output. The encoder E keeps the first three coordinates. The reduced transition G and output D satisfy EA=GE and DE=H exactly, where A and H are the original transition and readout. The seed is encoded as well. The existing cost-quotient engine checks these rational identities and solves only the reduced transfer system. Its resulting output generating function equals the original population function as a rational identity.

Independent integer matrix iteration checks 257 initial outputs against the allocation count formula. A separate timing run checks 4,096 outputs from both models. These prefix comparisons detect implementation errors but are not the reason for the all-time mathematical transport statement. The intertwining and readout identities provide that relationship. The general Lean release proves all-time transport through such identities; the concrete six-state packet here is replayed in Python and has not been separately instantiated and accepted by Lean.

The three-state response is also minimal among finite rational linear realizations of the same entire sequence. Its response Hankel block is formed from the first five coefficients, and its determinant is nonzero. Such a block cannot factor through a state space of dimension less than three. The retained Lean foundation proves the general Hankel factorization and dimension lower bound. This concrete determinant and rational realization are checked computationally. A lower bound among linear realizations says nothing about arbitrary nonlinear encodings or machines whose state consists of an unbounded integer with a different computation model.

This is the connection to DynaComp: a protected response can survive exact state reduction, and its entire future can be represented by a rational series. The repository's DynaComp adapters accept the actual linear and switched packet languages and replay their identities. The showcase constructs its own transparent source model rather than reporting a DynaComp application workload. That makes every coordinate and every discarded state available for inspection without disguising the example as independent industrial evidence.

## From a formal count to a convergent value

The same population function can be evaluated at z=1/8. Its exact rational value is 512/441. The showcase retains 24 coefficients and bounds the remaining infinite series using a pole-free disk test at radius 1/4. At that radius, the absolute weighted denominator mass is less than one, so the rational majorant supplies a coefficient envelope and a geometric remainder bound. Exact rational arithmetic verifies that 512/441 lies between the partial sum and that partial sum plus the reported bound.

This stage connects the counting representation to a convergent infinite sum. It uses an explicitly successful sufficient disk test; the implementation may refuse a radius even when another analytic argument could prove convergence there. The retained Lean series foundation derives coefficient majorants from normalized recurrences and proves the corresponding infinite-tail inequalities. Full refinement of every Python packet constructor remains separate. The exhibit therefore labels its new calculation as exact Python execution with a source-matched mathematical foundation.

The finite-sum panel uses the recent binomial-square compiler. A discovered, replayed recurrence reconstructs the sum of binomial(n,k)² over 0≤k≤n, with both endpoints accounted for. Its first 64 terms agree with independently computed central binomial coefficients. The source-bound Lean release already establishes the relevant retained recurrence for the actual finite sum, rather than an unnamed sequence fitted to data. The displayed perfect-power query is still a complete finite window, not an all-index classification of which sums are powers.

The stored-bits panel demonstrates a different entry point. Stored 0.25 is an exact rational square, whereas the exact binary64 value stored for 0.1 is not. The cancellation expression (10¹⁶+1)−10¹⁶ evaluates to zero under ordinary sequential floating arithmetic. Accumulating the exact stored operands and rounding once yields one. This concerns stored values and a declared arithmetic procedure, not the unknown real quantity a measurement might represent. The recent Lean release proves guarded stored-value semantics and the integer rounding decision; the entire Python encoder remains outside that completed refinement scope.

## What the measurements establish

The population benchmark compares the same count, selected member and objective maximum. Enumeration visits every allocation. The population route includes construction, count, selection, reverse rank, endpoint optimization and its independent oracle check. Five trials alternate method order. At budget 1,000, enumeration takes roughly 0.136 milliseconds and the general query roughly 12.96 milliseconds. At budget 100,000, enumeration still wins, about 14.17 versus 31.20 milliseconds. These costs are retained rather than hidden: a general mathematical representation is not free.

At budget 1,000,000, the measured medians are about 128.22 milliseconds for enumeration and 41.86 milliseconds for the population query. At budget 10,000,000, they are about 1,024.79 and 53.22 milliseconds, respectively. The trillion-budget query takes approximately 116.89 milliseconds. Enumeration at that budget was not performed or assigned an extrapolated timing. The saved ledger contains all individual measurements, runtime identity and the exact matched answers. Timings depend on the machine and load; regeneration measures them again.

The constructed machine benchmark takes approximately 13.12 milliseconds for six-state iteration and 5.09 milliseconds for three-state iteration over 4,096 steps. Dense matrix entry counts are 36 and 9 per step. Compilation and identity replay are excluded from those iteration timings. Sparse implementations, alternative recurrences and direct closed formulas would provide other baselines. These results show a local crossover and a local reduction benefit; they do not establish a broad solver or industrial speedup and do not replace the repository's previous industrial results.

## Reproduction and extension

Run `make exact-space-showcase` from the source checkout. It regenerates the exact result packet, timing ledger and standalone `receipts/exact_space/index.html`. Open that HTML file locally; there are no external scripts, fonts or service dependencies. Run `make exact-space-test` for independent bounded enumeration, objective ties, large-index checks, source-transport mutation rejection and the connected arithmetic results. The Python calculations use the standard library. The browser exhibit and saved receipts are included in the complete source archive.

The next useful application should supply a real allocation or observation problem and a meaningful baseline. It should state which coordinates, restrictions and outputs matter, measure compilation as well as repeated queries, and retain adverse cases. This exhibit supplies a compact route for doing that: one declared source problem, exact original-coordinate answers, a smaller response model, explicit proof coverage and reproducible costs.

An important extension would separate one-time model compilation from repeated queries against an unchanged model. The current population measurement intentionally constructs a fresh object each time, preventing a cache from making the demonstration appear cheaper than first use. A deployed application may reuse that object, but any such benefit should be measured and labeled separately. Another extension would compare the general engine against a specialized recurrence or a dedicated lattice-counting package on genuinely multidimensional restricted populations. Both directions would make the practical claim sharper without changing the exact meaning of the answers already demonstrated here.
