# PerfectPower: Play the Possibilities

The challenge makes exact allocation tangible through twelve original Petersen projects, five resource budgets and a complete answer. A visitor chooses cards, observes their exact total costs, asks for a hint, and compares the choice with a globally optimal group. All original project names, profits and resource cost columns are preserved. These are objective points, not currency or predicted financial returns.

For a seed s, a deterministic integer hash chooses an offset between zero and 38, then takes twelve consecutive projects from the original fifty. Each budget is the smaller of the original resource limit and the larger of the largest individual project cost and a seed-dependent fraction of the twelve-project cost sum, rounded down. The keep mode requires the first project; lean mode tightens ceilings to 85 percent while retaining a ceiling sufficient for the first project. These puzzle budgets are derived inputs, not the original fifty-project problem. Daily seeds are UTC dates, explicitly labelled; replay seeds and modes are encoded in URLs.

Let x range over {0,1}^12, with profits p_j and costs a_kj. Feasibility requires sum_j a_kj x_j <= B_k for each of the five resources and, when required, x_0=1. The complete population is the sum over all x of the product of these indicator factors. The shipped PerfectPower browser sum-product factor counter evaluates that sum in BigInt arithmetic. Optimization exhausts the same finite domain, retaining every mask whose exact integer score sum_j p_j x_j is maximal. The integers here are safely within JavaScript's exact integer range; population accumulation uses arbitrary-size integers. This is actual executable computation, not an animation or prerecorded answer.

Every hint names one differing bit relative to a calculated maximizing mask, with an explicit explanation that more changes may be needed to restore feasibility. Reveals recompute the user's score, show population and tie counts, and state additions, removals and exact resource use. Invalid user choices remain editable but never count as feasible achievements. Empty choices count unless a project is required. Alternative optimal masks are retained in exported evidence.

Replay links contain seed, mode and twelve selection bits expressed as an integer mask. Claimed scores in URLs are never trusted. Parsing rejects unknown modes, oversized masks and unsafe seed text. The receiving browser reconstructs inputs and calculates all results. No public leaderboard or server score submission is introduced. Share buttons use the device share sheet or clipboard, with a visible manual-copy fallback. Local progress is namespaced separately from native saved runs; storage failures leave the challenge playable. Local counters for starts, choices, hints, reveals and shares are not traffic analytics or visitor totals.

The landing experience includes an immediate challenge entrance, explanatory content for curious users and classroom use, links into the full fifty-project geometry and research Explorer, meaningful titles and descriptions, keyboard-visible controls, narrow-screen layouts and reduced-motion behavior. The geometric hero artwork is labelled illustrative. No invented data cloud represents the feasible population. Existing application identities and native download files remain intact.

Validation compares five seeds in each of three modes with an independent recursive subset walk, including population, optimal value, tie count and deterministic reconstruction. Browser workflows exercise project choices, budget excess, exact reveal, hint, optimal adoption, replay, local persistence, mode changes, evidence download, keyboard focus and phone width. Neither browser tests nor source packaging imply execution on physical Android or Windows hardware. Native executable upgrades are distinct from this browser release.
